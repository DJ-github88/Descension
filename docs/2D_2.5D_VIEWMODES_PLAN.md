## 1. Goal

Allow the GM to set, per map, how the tactical grid is presented:

| View mode | Grid type | Result |
| --- | --- | --- |
| `2d` | `square` | current topdown square grid |
| `2d` | `hex` | current topdown hex grid |
| `2.5d` | `square` | isometric square grid with elevation |
| `2.5d` | `hex` | isometric hex grid with elevation |

The existing `activeSceneMode: 'location'` exploration scene stays as a separate
dimension (pins / regional maps). GM-only switching; players follow. Portals between
maps keep per-map modes independent (a 2D area, an exploration area, a 2.5D hex area).

Hard requirements:
- Elevation for tiles, walls and tokens, raised **and** lowered (pits).
- Lights, vision and shadows must compute and render correctly with elevation.
- Rotatable camera (not fixed): GM sets a per-map default orientation, players may
  orbit locally. Free rotation + snap modifier.
- Hybrid rendering: SVG for walls/elevation/props (pickable 3D faces), Canvas2D for
  terrain/fog/light masks, DOM for tokens/items.

## 3. Data model

### Client
- `gameStore`: `viewMode: '2d'|'2.5d'`, `viewRotation` (yaw°, 0=north, player-local),
  `viewTilt` (pitch°, 2.5D only; 2D locked to 90°), setters + clamps.
- `mapStore.createDefaultMap`: `viewMode`, `cameraRotation`, `cameraTilt` (GM defaults),
  `elevationData: {"x,y": level}`, `rampData: {"x,y": {dir|type}}`,
  `sunSettings: { azimuth, elevation, color, intensity, ambient }`.
- `levelEditorStore` wall records (additive): `height`, `baseElevation` (defaults from
  `WALL_TYPES`, e.g. walls 10ft, windows full height, magical barriers 10ft).
- Elevation levels are integers in 5ft units (0 = ground, negative = pits).

### Server
Mirror the same fields in:
- `server/handlers/roomHandlers.js` default map skeleton,
- `server/handlers/socketHandlers.js` `validateMapExists`,
- `server/handlers/mapHandlers.js` `map_update` / `sync_map_state` /
  `sync_level_editor_state`,
- `server/handlers/validationService.js` Joi schemas.

Grid/orientation additions ride the existing `gridSettings` payload; elevation, ramps,
sun and lights ride the map-state payloads like `terrainData`.

## 4. Projection & camera orbit

New `vtt-react/src/utils/ProjectionSystem.js` (single source of screen math):

- Ground transform = `R_yaw(θ) → tilt → scale → translate` — affine, so:
  - canvas layers keep using `ctx.setTransform` (grid, terrain, fog masks, light pools,
    drawings, backgrounds);
  - `screenToWorld` inverse stays exact for ground picking.
- Vertical offset: screen `y -= z * zScale` (vertical axis stays screen-vertical in dimetric).
- Hex: project `getHexCorners` through the same transform.
- `depthKey(x, y)` = camera-forward projection (replaces fixed `x+y` for token z-index and
  SVG painter order). Cache projected geometry per rotation bucket; free rotation throttled
  to RAF.
- Pan deltas inverse-rotated in `Grid.jsx` (`moveCameraBy`); mouse-anchored zoom unchanged.

### Orbit UX
- Q/E free yaw, modifier+middle-drag, snap modifier for 45°/90° steps, compass HUD,
  reset-to-north. Pitch slider/blend in 2.5D only (clamp ~15°–90°).
- Persistence: per-map GM default (`mapStore`, synced) + player-local override (`gameStore`).
  On map transfer apply the destination default, then players orbit freely.
- Orbit never changes vision, facing, sun azimuth, fog data, or pathfinding geometry —
  only projection, picking, depth sort, pan.

### Occlusion
Tall structures (walls, cliffs) and tokens must share one depth space so a token can render
behind a wall. SVG ground content sits in a transformed `<g>`; extrusions are projected per
element (top face = ground polygon translated by height; side faces = quads). Tokens/items
interleave via a single depth-indexed z scale.

**Implemented (2026-09-12):**

- `utils/WallGeometry.js` is the single source of truth for projected wall/pillar geometry:
  world endpoints (square + hex), base elevation from the *highest* adjacent tile,
  camera-facing face selection, world-space sun shading, window/door sub-geometry and
  corner-node pillar specs. `SvgWallLayer`, `WallPicking` and `WallOcclusion` all consume it.
- `SvgWallLayer` renders (painter order: run shadows → depth-sorted side faces with their
  base lines → top faces), with real window assemblies (breast wall, lintel, jambs, glass
  panes + mullions, bars, arrow slits) and door states (planked leaf, bands, handle/lock,
  swung leaf + floor arc when open) as per-wall features. There are no pillars/posts:
  connected walls of the same material and height are merged with `polygon-clipping` into
  one union polygon and extruded as a single prism, so corners, T-joints and runs have no
  internal seams or overlapping faces at any camera angle. Side faces use a multiplicative
  ambient+diffuse world-space light (`mulColor`) plus a soft vertical gradient, a base
  contact line and a light top bevel; the texture pattern is world-aligned and subtle.
  Shadows are skipped whenever fog of war is enabled (and for FOV-dimmed runs) so walls do
  not leak through unexplored areas. Nearer raised terrain is still masked out of runs.
- `utils/WallOcclusion.js` replaces the old silhouette/bounding-box heuristic with exact
  world-space ray tests: analytic ray-vs-wall-slab and a DDA ray-vs-terrain-top march.
  This supports wall heights, base elevation, pits and looks "over" low walls at steep
  tilt without false positives.
- Tokens/items/containers that a ray reaches through a wall, pillar, cliff or pit rim get a
  stippled ring plus reduced opacity and saturation (`.token-occlusion-ring`), and the flag
  is recomputed only when the view angle, wall data or elevation data changes.

## 6. Vision, lights & shadows (elevation-aware — hard requirement)

World-space math only; camera orbit affects projection alone.

1. **Light sources** carry world position + elevation (`z`), radius, intensity, color,
   flicker, optional cone direction. Falloff is computed from source elevation; a source
   below a cliff edge does not light the raised top unless the geometry allows.
2. **Eye-height LOS**: wall segment occludes when `wallTop > viewerEye` on the ray, and
   target eye level; viewers on high ground see over low walls; viewers in pits are occluded
   by the rim. Rule table documented and unit-tested before wiring.
3. **Shadows**: projected from wall/cliff prisms along per-map sun
   (`azimuth`, `elevation` angle) and from point-light cones. Raised terrain casts onto
   lower ground; pits receive light from above and cast rim shadows.
4. **Fog reveal**: `lightInteractsWithFog` stays wired; light tiles only reveal what the
   elevation-aware LOS allows.
5. **Fix while wiring**: light `gridX/gridY` vs `x/y` mismatch (standardize on world px,
   matching tokens); `blocksVision` must read `WALL_TYPES[type].blocksLineOfSight`.
6. Render in 2.5D: light pools as projected gradients, shadow polygons as projected SVG
   (or canvas mask for the ground plane).

## 10. Risks & mitigations

- **Depth interleaving (SVG faces vs DOM tokens)** — single depth-indexed z scale; LOD caps.
- **Free-rotation sort cost** — cache per bucket, RAF throttle, snap defaults to 45/90.
- **Hex+iso geometry** — affine projection of hex centers; golden tests for corners.
- **Approximate 3D LOS** — codify rules table + tests before wiring.
- **Payload growth** — `map_updateBatcher` + Firestore 100KB split; delta fields if needed.
- **Dead stubs** — remove/repurpose `isometricView`/lighting panel wiring to avoid dual
  sources of truth.
- **Known regressions to protect** — fog/afterimage trail pruning, wall-drop validation,
  token ownership, AP confirmation (see Mind `fog-memory-system-architecture`,
  `player-pan-trail-prune-wall-drops`, `ap-movement-confirm-system-fixes`).

## Fix — 2026-09-12: hex brush footprint parity

Hex terrain tools previewed a hex ring (`hexDistance <= floor(size/2)`) while the paint/erase/
elevation stores stamped a `size x size` block in axial (q,r) space; the block's diagonal corners
`(q±1,r±1)` were painted outside the preview, so the painted footprint looked shifted in both 2D
and 2.5D.

- One shared footprint source: `computeBrushTiles()` in `utils/InfiniteGridSystem.js` (hex ring
  for hex maps, legacy `size x size` block for square maps; non-numeric sizes normalize to 1),
  exposed as `gridSystem.getBrushTiles()`.
- Consumers now all use it: `TerrainHoverPreview`, `paintTerrainBrush`, `removeTerrainAtPosition`,
  `paintTerrainLine`, `removeTerrainLine` (levelEditorStore) and `applyElevationStamp`
  (ProfessionalVTTEditor).
- Coverage: `src/utils/__tests__/BrushFootprint.test.js` (ring/block geometry + store paint/
  erase/line integration). Suite now 91 suites / 1353 tests.
