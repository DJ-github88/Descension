### 1.16 Hard conclusions (what this means)

1. Mythrill already has **the entire authoring DNA** for conditional behaviors (priority bands, trigger pickers, combat-style fields) and **none of the runtime**. The evolution is therefore not “invent behavior,” it is “give the authored intent a small, safe evaluator and GM surfaces.”
2. The existing priority model is a **d20 band model** (“Roll X–Y to use”). Any new weighting must preserve that ontology, both for tabletop equivalence and to avoid invalidating authored content.
3. The **quick-use flow already has the correct GM-safety shape** (pick ability → confirm costs → spend → chat). Evolution should extend that dialog with target/aspect/telegraph options rather than build a parallel path.
4. Digits for a telegraph layer already exist (AoE geometry + wall clipping + affected-token detection + persistent overlay). A telegraph is “an AoE template with a lifecycle.”
5. The largest risk is **logic absorption into giant components/stores** (see §15). The engine must be a pure library with a tiny store/store-integration surface.

## 2. DESIGN PRINCIPLES

1. **GM is the AI.** The engine suggests, explains, and executes on click. It never takes a turn on its own. Automation reduces cognitive load (rank, explain, preview) and never removes control.
2. **Every rule is table-playable.** If a mechanic cannot be written on a one-page statblock and adjudicated with dice and markers, it does not ship.
3. **Preserve the existing randomness language.** DICE / CARDS / COINS priority bands remain the base; conditional weighting modulates them rather than replacing them.
4. **Normal creatures stay simple.** Behavior, aspects, and telegraphs are all optional blocks. A creature with none behaves exactly as today.
5. **No monster-specific code.** A dragon wing is an instance of a generic aspect capability; the engine only knows declarative fields.
6. **Additive schema.** Old creatures, old saves, old rooms, and old clients must not break. Unknown fields are ignored; new fields default to no-op.
7. **One source of truth per datum.** Definitions live on the creature (library); instance state lives in token state; live threats (telegraphs) live in a dedicated store; all three sync through the existing multiplayer token/room channels.

## 3. PROPOSED SCHEMA (additive, namespaced)

No existing fields are renamed or reinterpreted. All new blocks are optional.

### 3.1 Condition grammar (shared by weights, transitions, telegraphs)

A condition is a small tree of table-adjudicable predicates. Proposed leaf vocabulary (each line names the physical-table check):

```jsonc
// self / target / anyAlly / anyEnemy scope prefixes omitted for brevity
{ "hpPctLte": 50 }                       // "is my HP at/under half?"
{ "targetHpPctLte": 25 }                 // target statblock marker
{ "hasCondition": "burning" }            // status marker on the mini
{ "isIsolated": "target" }               // no allies within 10 ft
{ "distanceLteFt": 30 }                  // ruler
{ "enemiesWithinLteFt": { "count": 2, "radiusFt": 10 } }  // "surrounded"
{ "alliesWithinLteFt": { "count": 1, "radiusFt": 10 } }
{ "aspectState": { "id": "left_wing", "state": "damaged" } }
{ "flag": "flying" } / { "flag": "grounded" } / { "flag": "wet" } / { "flag": "burning" }
{ "roundGte": 3 }
{ "previousAbilityIs": "glacial_breath" }
{ "terrainFlag": "water" }               // GM-toggled battlefield state
```

Combinators: `{ "all": [ ... ] }`, `{ "any": [ ... ] }`, `{ "not": { ... } }`.
All predicates must be answerable in <5 seconds at a physical table. GM toggles (`terrainFlag`, manual aspect states, manual flags) are the pressure valve for anything ambiguous.

### 3.2 Behavior block (creature-level)

```jsonc
"behavior": {
  "version": 2,
  "baseWeights": { "rime_claw": 11, "glacial_breath": 3 },   // optional; overrides priorityRange-derived
  "modifiers": [
    { "id": "cornered", "when": { "enemiesWithinLteFt": { "count": 2, "radiusFt": 10 } },
      "add": 8, "label": "Surrounded: fights wilder" },
    { "id": "rime-on-wet", "when": { "all": [ { "flag": "wet" }, { "target": true } ] },
      "mul": 1.5, "label": "Rime clings to wet targets" }
  ],
  "stateTransitions": [
    { "id": "enrage", "when": { "hpPctLte": 50 }, "to": "enraged",
      "once": true, "modifiers": [ { "when": {}, "add": 4, "label": "Enraged" } ],
      "chat": "Skornvind's rime boils." }
  ],
  "resolver": "DICE"    // DICE (default) | CARDS | COINS — matches priorityRange language
}
```

**Weight resolution (pure, deterministic given inputs):**

1. `base = behavior.baseWeights[id] ?? priorityRange-derived(id) ?? 10`.
   - `priorityRange` derivation: `band = max - min + 1` for DICE; for CARDS/COINS, estimated success probability × 20, floored at 1. This makes band width == weight, i.e. exactly today's “Roll X–Y to use.”
2. For each modifier whose `when` passes: `w = (w + add) * mul`, then clamp to `[min, max]` if present.
3. Total weight maps onto a d20 band table (cumulative proportion, minimum band 1). The rolled d20 lands in exactly one ability band (ties ordered by authored list order).
4. Engine returns `suggestions[]` each with `{ abilityId, base, final, band: {min,max}, applied: [{id,label,add,mul}], affordability, disabledBy }`.

**Why-is-this-weighted:** the `applied` array *is* the explanation; the GM popover just renders it. No modifier may exist without a `label`.

**GM override:** suggestions are advisory. Manual ability clicks are always available and never filtered by weights, only by cost/disabled conditions (with a visible GM “ignore costs/conditions” toggle, as today's chat-only flow is effectively cost-enforced but not condition-enforced).

### 3.3 Aspects block (creature-level definition)

```jsonc
"aspects": [
  {
    "id": "left_wing",
    "name": "Left Wing",
    "kind": "wing",                       // open vocabulary: wing|tail|claw|eye|armor_plate|venom_gland|ritual_focus|will|...
    "track": { "type": "hp", "max": 40 }, // or { "type": "states", "states": ["intact","damaged","destroyed"] }
    "states": [
      { "id": "damaged",   "when": { "hpPctLte": 50 } },
      { "id": "destroyed", "when": { "hpPctLte": 0 } }
    ],
    "exposed": { "damageTypes": ["slicing"], "bonusPct": 25 },   // striking the wing is easier
    "disables": ["wing_buffet"],
    "grantsWhenDestroyed": { "flag": "grounded" },
    "visual": { "icon": "...", "overlay": "wing-crack", "tooltip": "..." },
    "telegraphable": true
  }
]
```

Instance state never lives on the definition:

```jsonc
// token.state.aspects
{ "left_wing": { "current": 22, "state": "damaged" }, "rime_gland": { "current": 25, "state": "intact" } }
```

Engine rules:

- Abilities may declare `"requiresAspects": ["rime_gland"]` and `"disabledWhen": [{ "aspectState": { "id": "rime_gland", "state": "destroyed" } }]`.
- Damage routing to an aspect is always **GM-declared** (dialog option), never automatic. If routed, `exposed` applies; the aspect consumes first; overflow optionally continues to HP (per `overflowToHp: true`).
- State changes cascade through declarative fields only (`disables`, `grantsWhenDestroyed`, `modifies`), which the engine evaluates generically.
- **No monster-specific code is permitted. New creature concepts must be new `kind` strings plus declarative data.**

### 3.4 Telegraph block (ability-level)

```jsonc
"telegraph": {
  "windup": { "until": "end_of_round" },        // end_of_round | start_of_source_next_turn | after_player_actions
  "shape": { "type": "cone", "sizeFeet": 30 },  // reuse AOE_SHAPES geometry
  "anchor": "self",                              // self | targetPoint
  "interrupts": [
    { "id": "break_gland", "when": { "damageToAspectGte": { "id": "rime_gland", "amount": 15 } },
      "result": "fizzle", "aspectState": "destroyed", "label": "Shatter the rime gland" }
  ],
  "resolve": { "damage": { "formula": "3d8", "type": "rime" }, "save": { "ability": "agility", "dc": 14, "outcome": "half" } }
}
```

A telegraph is instance data, not definition data:

```jsonc
// telegraphStore (new, small)
{ "id", "roomId", "mapId", "sourceTokenId", "abilityId", "anchor", "shape", "sizeFeet",
  "rings": [...], "createdRound", "resolveAt", "state": "pending|interruptible|resolving|resolved|fizzled",
  "responses": [ { "type": "damage", "tokenId", "amount", "at" } ] }
```

### 3.5 Creature state block (instance)

```jsonc
// token.state.creatureState
{ "tags": ["bloodied", "enraged", "grounded"],       // derived state names
  "since": { "bloodied": { "round": 2, "turn": 1 } } }
```

Named tags come from `behavior.stateTransitions` (data). The engine does not invent tags; `bloodied`/`enraged`/`grounded` are simply convention names used by this design. Conditions remain separate in `token.state.conditions`. This avoids monster-specific booleans and keeps one generic transition table.

## 4. EVENT FLOW (suggest → respond → resolve)

```
GM turn starts (combatStore.nextTurn / manual selection)
  └─> behavior engine builds context snapshot (pure reads):
        creature definition + token.state + aspects + conditions
        + combat round/turn + tokens/creatures + map flags
  └─> evaluate stateTransitions (idempotent, once-guards)
  └─> score abilities (base bands + modifiers) → suggestions[] with traces
  └─> BehaviorSuggestionPanel renders top suggestions + "why" + manual list
        │
        ├─ GM picks suggestion or manual ability
        │    └─> target selection (targetingStore), optional aspect target
        │    └─> CreatureAbilityConfirmDialog (extended):
        │           cost / aspect routing / telegraph preview / GM override
        │    └─> EXECUTE (pure helper):
        │           spend AP/mana (existing updateTokenState + combatStore)
        │           apply aspect track/state changes (token_updated)
        │           if ability.immediate: roll damage/save, apply via
        │              resistance helper (existing effectProcessingService math
        │              + manual GM adjust), log combat chat
        │           if ability.telegraph: telegraphStore.create + overlay +
        │              broadcast telegraph_created + room persist
        │
        └─> any time before resolveAt: GM force-resolve / force-fizzle
              players use normal reactions (existing AP flows, no new economy)

telegraph resolution (engine subscriber, not combatStore-internal):
  resolveAt reached (round/turn change or GM action)
    └─> compute final affected set from LAST committed rings (tokens may have moved)
    └─> damage/save once, log, set state=resolved, broadcast+persist, remove overlay
```

Reactions remain exactly as authored in the rulebook (`rules.json:3386-3552`): spend AP, specific trigger. The engine only *advertises* a response window; it does not automate reaction eligibility or grant AP.

## 5. STATE FLOW

```
token.state.currentHp changes (any path: menu, TargetHUD, DOT, ability)
  └─> behavior engine (subscriber after damage) evaluates stateTransitions
        healthy→bloodied (hpPctLte 50): add tag, optional weight modifiers, visual
        will-track depleted:         add tag, escape state (GM may override)
  └─> if a transition disables a pending telegraph's required aspect → fizzle
  └─> suggestions recompute on next read (no stored scores)

aspect track change (GM-declared strike; or telegraph interrupt)
  └─> token.state.aspects updated → state derived from declarative thresholds
  └─> disables[] and grantsWhenDestroyed applied by engine
  └─> telegraph interrupts evaluated (damageToAspect ≥ N → fizzle + destroy)

round/turn changes (existing nextTurn pipeline)
  └─> telegraph resolveAt checks (engine subscriber)
  └─> state transition re-check (turn boundaries catch DOT-driven threshold crossings)
```

All state lives in exactly one place: `token.state.*` (HP/aspects/tags), `telegraphStore` (threats). Nothing is duplicated into components.

## 6. UI FLOW / GM UX

New small components (proposed home `src/components/creature-behavior/`; existing naming style):

1. **`BehaviorSuggestionPanel`** — for the current creature:
   - header: name, HP bar, state chips (bloodied/enraged/grounded), RE-ROLL button (uses authored resolver), “Roll behavior (d20)” result.
   - rows: icon, ability name, band (`7–12`), final weight, cost, `why?` expander listing applied modifiers with labels.
   - actions per row: `[Use]` (opens target + confirm), `[Card]` (spell card popover), plus a top “Choose manually…” list of all abilities.
   - multi-creature mode: when the GM opens the panel during combat, it follows the current turn and can be pinned; a compact “next 3 creatures” strip supports running packs without opening each sheet.
2. **`AnatomyPanel`** — only rendered when `creature.aspects?.length`:
   - chips with track value or state; hover tooltip lists `disables`/`grantsWhenDestroyed`/`exposed`; GM click sets state manually (override).
   - used both in the suggestion flow (target an exposed aspect) and in inspect/window views.
3. **`TelegraphLayer`** — canvas overlay sibling of `SpellAoEOverlay`, reusing `buildAoEPolygon` + `clipAoEAgainstWalls` + `getTokensInAoE`:
   - pending pulse animation, countdown label (“resolves end of round 3”), GM context menu (resolve/fizzle/edit).
4. **`TelegraphResponseBar`** — visible to players: threat name, shape/label, time remaining, “your AP: 2 — reactions available,” and a link to the relevant reaction rules; purely advisory.
5. **Why-is-this-weighted** is part of (1), not a separate window.

Integration rule: `CreatureToken.jsx` changes are limited to mounting `BehaviorSuggestionPanel`/`AnatomyPanel` from its existing window/context-menu surface and rendering `TelegraphLayer` badges; **no engine logic and no new behavior branches** inside it. `CreatureAbilityConfirmDialog` gains optional target/aspect/telegraph sections; its cost-spend core is untouched.

Design guardrails for cognitive load: default view shows max 3 suggestions + manual fallback; all suggestions require one click; no popups spawn without GM action; the panel is dismissible and never blocks the canvas.
